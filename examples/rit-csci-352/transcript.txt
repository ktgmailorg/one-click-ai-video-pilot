Now define System Calls & Privilege Levels precisely enough that another learner could

test the definition.

A system call transfers control from user code to a privileged kernel service.

Consider this worked case: When a program requests disk I/O, it executes a system call

instruction that switches execution to the kernel to handle the request.

Separate the formal definition from an implementation detail, then identify what

evidence would distinguish them.

A precise definition makes later examples easier to evaluate and revise.

With the foundation in place, examine how Traps & Processor State operates in a concrete

sequence.

A trap records processor state so the kernel can handle a system call, exception, or

interrupt.

Consider this worked case: When a page fault occurs, the CPU traps the faulting

instruction, saves the instruction pointer and registers, and transfers control to the kernel

handler.

Follow every arrow in order and name the state before and after each transition.

The trace converts an abstract statement into an inspectable sequence.

Next, compare the choices involved in Page Tables & Virtual Memory and make the decision

criteria explicit.

Page tables map virtual addresses to physical memory with permission bits.

Consider this worked case: A page table entry for a read-only code segment contains a valid

bit, a present bit, and a read-only permission flag.

Compare alternatives against the same constraints so the evaluation does not move

the goalposts.

Using shared criteria turns a preference into a defensible technical choice.

Apply Processor Scheduling to a worked situation instead of treating it as an

isolated definition.

The scheduler selects runnable processes and switches processor context.

Consider this worked case: The OS scheduler picks a ready process from the run queue,

saves the current process's registers, and loads the new process's context.

Work from the concrete inputs to the result, checking units, types, or invariants at each

step.

The worked case shows both how to apply the method and how to check it.

Examine the tradeoffs in Locks & Synchronization, including what improves and

what becomes more difficult.

Locks protect invariants when concurrent execution can access shared state.

Consider this worked case: A mutex lock ensures that only one thread can modify a

shared counter at a time, preventing race conditions.

State the benefit, the cost, and the condition under which the tradeoff is acceptable.

Making the tradeoff visible prevents a local improvement from hiding a larger cost.

Name each dependency explicitly, and keep labels and representations consistent

Stress-test the reasoning around Deadlock & Resource Management with an edge case and

Analysis distinguishes user mode, privileged kernel code, hardware translation, interrupt

Consider this worked case: Two processes each hold one file descriptor and wait for the

Change one assumption at a time and observe which part of the reasoning no longer holds.

Use Multiprogramming & Multiprocessing to diagnose a failure by separating symptoms,

Topics include process synchronization, interprocess communication, deadlock,

Consider this worked case: A server handles multiple client requests simultaneously by

Locate the first point where observed behavior diverges from expected behavior, then test the

Connect File Systems & I/O to the earlier ideas and explain how the pieces work as one

The file system organizes persistent data through inodes, directories, and logged

updates.

Consider this worked case: A directory entry points to an inode that stores file metadata,

permissions, and block addresses for data storage.

Explain each connection explicitly and verify that information retains the same meaning

Finish with Practical Analysis Checklist as a practical checklist that can guide a new

analysis.

Architecture analysis preserves data dependencies, control dependencies, and

architectural state.

Consider this worked case: Audit a kernel module to ensure all shared variables are
