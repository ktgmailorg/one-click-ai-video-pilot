By the end of this lesson, you will be able to trace one RISC-V ADD instruction from its

thirty-two encoded bits to the value written into a destination register.

You will also be able to explain why a pipeline improves throughput, identify data

and control hazards, and distinguish architectural correctness from implementation

speed.

Our worked instruction is add x5, x6, x7.

We will use a classic five-stage teaching pipeline: Instruction Fetch, Instruction

Decode, Execute, Memory Access, and Write Back.

That pipeline is not the only possible processor design.

It is a clear model for seeing how encoded instructions become coordinated data movement

and control.

First, separate the contract from the machinery.

The RISC-V ISA says what ADD means: read two source registers, add their values, and write

the low XLEN bits into the destination register.

It also specifies the instruction fields that identify that operation.

Software depends on this promise.

Internally, one processor might execute an instruction in several simple stages, another

might issue multiple instructions at once, and a small controller might reuse hardware across

many cycles.

Those designs may look very different, yet a correct implementation must produce the same

software-visible result.

This distinction keeps our reasoning disciplined: begin with what must happen, then

study how one pipeline makes it happen.

The processor receives bits, not assembly text.

Our instruction word is hexadecimal zero zero seven three zero two B three.

Reading the R-type fields from bit thirty-one down to bit zero gives funct seven, rs2, rs1,

funct three, rd, and opcode.

The opcode says this is a register-register arithmetic instruction.

Funct three and funct seven narrow that family to ADD.

The rs1 field is binary zero zero one one zero, which names x6.

The rs2 field names x7.

The rd field names x5.

Decode therefore extracts both the operation and the register addresses from one

fixed-width word.

The assembly form is a human-readable rendering of those exact fields.

Assume the program counter contains zero x one thousand.

Fetch presents that address to instruction memory and receives the thirty-two-bit ADD

word.

At the same time, the processor forms the sequential next address, zero x one thousand

four.

That plus-four step is valid for this RV32I teaching example because we are not using

compressed instructions.

Fetch does not yet know whether control flow will remain sequential.

A branch or jump may later redirect the program counter.

For now, the current address, instruction bits, and predicted next address must remain

aligned as the instruction moves forward.

Pipeline state records the information the Decode stage will need on the next clock

cycle.

In Decode, the instruction fields drive two related jobs.

First, the register file uses rs1 and rs2 as read addresses.

If x6 contains nineteen and x7 contains twenty-three, those values appear on the two

read ports.

Second, control logic interprets the opcode and function fields.

It selects an integer addition, chooses two register operands for the ALU, disables a

data-memory write, and enables a later register write to x5.

Data alone is not enough.

The destination register number and every control decision needed by later stages must

advance beside the operands.

If a value and its control signal become misaligned, the processor could compute

correctly but write the result to the wrong place.

The Execute stage supplies nineteen and twenty-three to the arithmetic logic unit.

Operand-select controls choose the two register values, and the ALU control selects

addition.

The result is forty-two.

In RV32I, XLEN is thirty-two, so ADD retains the low thirty-two bits of the mathematical

sum.

If the signed mathematical result exceeds the signed range, ADD still produces the low-bit

result; it does not raise an arithmetic-overflow exception.

The ISA defines that behavior, while the ALU and surrounding control implement it.

For this example there is no overflow, so the value forty-two and the destination number x5

advance toward the next stage.

ADD does not need a data-memory read or write.

Even so, in this regular five-stage organization it occupies the Memory stage

while its ALU result, destination register, and write-enable bit move through the EX slash

MEM and MEM slash WB pipeline registers.

A load instruction would use this stage to read data, and a store would write data.

ADD simply preserves its result.

In Write Back, a result-select control chooses the ALU value rather than memory data, the

write-enable signal is asserted, and x5 receives forty-two.

At that moment the instruction's promised architectural effect becomes visible in the

register file.

Why split the work into stages?

Because different instructions can use different hardware during the same cycle.

While our ADD is in Execute, a following independent instruction can be in Decode and

another can be in Fetch.

During the next cycle, all three advance.

After the pipeline fills, this ideal sequence can complete roughly one instruction per cycle

even though each instruction spends several cycles traveling from Fetch to Write Back.

That is a throughput improvement, not proof that one instruction has lower latency.

The clock period must accommodate the slowest stage plus pipeline-register overhead, and the

ideal completion rate assumes instructions can advance without interruption.

Now place sub x8, x5, x9 immediately after the ADD.

The subtraction needs the new x5 as an input, but ordinary register-file timing may not

provide that value when the subtraction reaches Execute.

This is a read-after-write hazard: the later instruction reads a register that the earlier

instruction will write.

Hazard logic compares the source registers of younger instructions with destination

registers already in the pipeline.

Detecting the name match is only the first step.

The processor must also know whether the value is ready and where it currently resides.

Correctness requires the subtraction to use forty-two, not the stale value previously

stored in x5.

For an ALU-to-ALU dependency, forwarding can often avoid a full wait for Write Back.

A bypass path routes the ADD result from a later pipeline register directly to the

subtraction's ALU input.

The register file may still contain the old x5, but the operand multiplexer selects the

newer forwarded value.

Forwarding does not solve every dependency.

If a load produces data only after Memory Access and the next instruction needs it

immediately, the value may arrive too late for the dependent Execute stage.

Hazard control then freezes selected pipeline state and inserts a bubble.

One cycle of lost throughput is preferable to an incorrect result.

Branches create a different uncertainty.

Fetch wants a next address every cycle, but the branch decision and target may not be

known immediately.

A simple processor can wait.

A faster design may predict a direction and continue fetching.

If the prediction is wrong, the processor redirects the program counter and flushes

younger wrong-path instructions before they change architectural state.

A flush is not merely erasing a diagram box.

It disables the invalid instructions' control effects so they cannot write registers or

memory.

Prediction can improve average performance, but recovery logic preserves correctness when

speculation is wrong.

Performance language needs precision.

In an idealized scalar pipeline, the steady-state cycles per instruction can

approach one.

Real execution includes pipeline filling and draining, data stalls, control redirects,

cache delays, and other constraints.

A useful first model is actual CPI equals the ideal baseline plus the average stall cost per

instruction.

This is not a universal performance equation for every processor; it is a teaching

decomposition.

Clock rate also matters.

Deeper pipelines can shorten some stage delays, but they add registers, control

complexity, and potentially larger recovery penalties.

Architecture evaluation therefore considers both work completed per cycle and the duration

of each cycle.

We began with the word zero x zero zero seven three zero two B three.

Decode identified ADD, rs1 x6, rs2 x7, and destination x5.

Fetch read the instruction at zero x one thousand.

Decode read nineteen and twenty-three.

Execute produced forty-two.

Memory Access performed no data-memory operation.

Write Back committed forty-two to x5.

Independent instructions could overlap, while dependencies or branches required forwarding,

stalls, redirects, or flushing.

To test your understanding, ask four questions about any instruction: What operation do the

bits encode?

Which values enter each stage?

Which control signals must travel with them?

And can any younger instruction proceed without violating the ISA result?

If you can answer those, you can reason about the pipeline rather than merely memorize its

five boxes.
